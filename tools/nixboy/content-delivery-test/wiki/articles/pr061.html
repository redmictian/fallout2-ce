Mechanism → observation → warranted diagnosis

A large number
is not a diagnosis.

A process can own a large address range while using little RAM. A disk can have free bytes while refusing another file. Learn what each measurement counts before deciding which resource limits the work.

Address space is a view; RAM contains pages

A program issues loads and stores using virtual addresses. Its address space is divided into ranges called mappings. A mapping describes permitted accesses and a backing source: for example, a file or anonymous memory. Page tables connect virtual pages to physical page frames when a usable translation exists. Protection checks apply during access. A mapped range is therefore a promise about addresses and permissions, not proof that every byte currently occupies a distinct RAM byte.

The usual base page on x86-64 is 4 KiB, but discover the value with getconf PAGESIZE. Huge pages exist; this pilot's exact arithmetic explicitly assumes ordinary 4 KiB pages. Virtual addresses in different processes are separate names: equal numeric addresses do not establish shared physical memory. Different virtual addresses can refer to the same frame.

Virtual size: how much is mapped?

VSZ in ps totals virtual address-space size in KiB. Large reserved or sparsely touched regions can inflate it. Adding every process's virtual size does not measure installed RAM demand.

Resident size: what is in RAM now?

RSS counts resident mapped pages for that process, including pages also mapped by peers. Summed RSS can count a shared page several times. RSS is a changing observation, not the maximum future requirement.

Proportional share: how is sharing charged?

PSS apportions a resident page across its actual sharers. A 4 KiB page resident in two process views contributes 4 KiB RSS and 2 KiB PSS to each. PSS is an accounting share; it is not a separate memory pool.

/proc/PID/maps lists ranges and permissions. The final p in r--p means a private mapping, not “all of these physical pages are already private.” Private file mappings can initially share clean backing pages. A mapping may permit writes while its current page-table entry remains read-only to trigger copy on write; a valid write can therefore fault without contradicting the mapping permission. A write that must be private can cause copy on write: allocate a private page and copy the old content. Conversely, a mapping eligible for sharing need not currently have another sharer. Read smaps accounting instead of guessing sharing from a permission letter.

A fault is a request for the kernel to resolve an access

On first use, a mapping may not yet have a usable page-table entry. The CPU traps to the kernel. A valid access can then proceed after the kernel installs a translation, supplies a zero-filled anonymous page, finds an already cached file page, copies a private page, or reads required data from storage. An invalid access may instead be rejected. Normal page faults are part of demand paging; the word “fault” does not itself mean a broken program.

Process fault counts and system fault counts have different scopes. A cumulative value describes history. To ask what happened during an incident, subtract observations around the same interval. A drop after PID replacement can be a different process, not an improvement.

Predict: a process maps 256 MiB and writes to one previously untouched 4 KiB page. Must RSS rise by 256 MiB?

No. The access concerns one page. Under our ordinary-page, no-prefaulting assumptions, that page needs backing and a translation; mapping the whole range did not require all 256 MiB to become resident. Kernel overhead and other process activity make real RSS changes less tidy than this model. That is why the worked arithmetic states its assumptions.

Used RAM can be useful, reclaimable, or under pressure

Linux uses otherwise spare memory for cached file contents and metadata. A repeated file read may be satisfied from the page cache instead of storage. A clean file page can be discarded and reread later. A dirty page needs appropriate writeback before it can be discarded. Private anonymous data has no unchanged file copy to reread; some of it can be moved to swap when swap is available. These paths have different costs.

Reclaim tries to free frames for other use. Background reclaim can prepare space; an allocating task may also perform direct reclaim and wait. If active demand repeatedly evicts pages needed again, the machine can spend substantial effort moving or reclaiming pages. With insufficient reclaimable memory it may reach an out-of-memory decision. A low MemFree figure alone establishes none of those events.

Use a bundle of evidence

MemAvailable is the kernel's estimate of memory available for new work without swapping. Compare it with interval changes in scan/steal counters, actual swap-in/out rates, task progress and the workload's known scope. A rise in pgscan counts pages examined during reclaim; a rise in pgsteal counts pages actually reclaimed. Scanning alone does not prove successful reclaim. Sustained cost and constrained progress establish why this activity matters here. A filled swap allocation can be historical. Zero swap traffic does not rule out file-cache reclaim, and a major fault is not automatically a swap-in.

Scope matters: /proc/meminfo, /proc/vmstat and ordinary vmstat describe the kernel's system view. A task's resource limit is not automatically that entire system's RAM. The supplied B assessment must expose a genuine controlled system observation domain; an unlabelled host-wide counter beside a per-process limit is insufficient evidence. Facilities are requirements to supply, not a prescribed hosting architecture.

Record times and subtract each counter's earlier value from its later value. pswpin/out counts pages whereas vmstat si/so has its own displayed units; do not compare bare numbers as though units match. A system counter includes other active processes. A useful diagnosis states that boundary instead of attributing every increment to the selected PID.

Bytes and inodes answer different capacity questions

A filesystem needs space for data and metadata. On filesystems with a finite inode supply, creating another object also needs a free inode. Thousands of empty files can consume inodes while using few data blocks. A full byte store and an exhausted inode supply can produce the same broad “no space” symptom. A permission refusal is a separate cause.

This pilot also uses tmpfs, an existing Linux memory-backed filesystem. It can have a configured byte limit and an independent inode budget. Its files use memory and can use swap; its configured free filesystem bytes are not the same measurement as system MemAvailable. A small object-count limit can therefore be reached while both filesystem bytes and system RAM have headroom. No mount administration is required here; the prepared assignment supplies the mount and its limits.

$ findmnt -T /srv/pr061-practice/volume/data/seed.txt
$ df -B1 /srv/pr061-practice/volume
$ df -i /srv/pr061-practice/volume

df -B1 reports allocated/available filesystem space in bytes; it is not a sum of visible file lengths. df -i reports inode capacity. The relevant mount can differ from the filesystem holding your evidence files. Reserved capacity and filesystem type affect interpretation; this pilot declares those starting facts. Do not delete data, resize a filesystem, clear caches or increase limits merely to obtain a smaller number. PR06.1 assesses observation and diagnosis, not repair.

Worked investigation: a slow export and a frightening VSZ

A prepared demonstration has four CPUs. The export is slower than its earlier same-work run. A helper process shows VSZ 3 GiB, RSS 24 MiB. These figures look dramatic beside only 2 GiB RAM. Before reading on, choose which next observation would separate “large address view” from “active memory pressure.”

The large virtual mapping is not evidence of a 3 GiB resident allocation. We have no observed reclaim pressure or storage-capacity failure in this interval. The changed concurrency is a plausible reason for reduced throughput, supported by unused CPU capacity and the supplied workload setting. That evidence is still a diagnosis to test: a controlled change and repeated same-work measurement are PR06.2. We have not proved a memory leak absent, predicted every future run, or established all wall-time causes.

The essential reasoning is to line up scope, interval and work: what resource, counted where, over what time, while doing how much correct work? The assessments change the limiting resource and the evidence, so “large VSZ is always harmless” is as weak as “large VSZ always means no RAM.”

A small exact model makes sharing visible

Assume two processes each map exactly the same 12 KiB of clean resident file pages and each has 20 KiB of distinct private resident pages. All pages are ordinary 4 KiB pages; there are no other sharers or pages in this model. Each RSS is 32 KiB. The two RSS values sum to 64 KiB, but distinct physical memory is 12 + 20 + 20 = 52 KiB. Each PSS is 20 + 12/2 = 26 KiB. PSS totals 52 KiB under these assumptions.

Predict: one process privately writes one shared 4 KiB page. What changes?

Assume the write needs copy on write and both old and new pages stay resident. Distinct physical use rises by 4 KiB. Both processes can still report RSS 32 KiB: each has the same number of resident virtual pages, but one page now has two physical copies. That contrast explains why an unchanged RSS does not prove unchanged sharing.

The same rule works for three sharers: divide only the common pages by three; private pages stay fully charged to their owner. With unequal private amounts, compute each process separately and count the shared physical pages once. Real processes have more mappings and changing sharers; use this exact model to interpret the counters, not to demand exact arithmetic equality between measurements collected at different instants.

Resume without racing a process timer

The supplied practice and assessment mappings wait without a timed exit. Load and peer processes remain available while the assignment is open, through reading and breaks, until explicit finish/reset. This is separate from taking five fresh CPU samples or two counter reads ten seconds apart. After a break, check identities and collect new intervals. Do not join counters across process replacement.
