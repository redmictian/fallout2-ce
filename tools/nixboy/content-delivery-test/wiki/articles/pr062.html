L-PR-C/performance-investigation · PR06.2

A measurement is evidence.
A correction is a test.

Find out where a real workload spends CPU time, distinguish that from elapsed time, change one permitted cause, and check whether equally correct work improves repeatedly.

What you will be able to establish

PR06.1 taught you to identify a resource symptom without treating a large number as its cause. Here you will build a bounded explanation for a slowdown. You will gather actual counters and a profile, compare them with another observation, make a permitted correction, and repeat both measurement and correctness checks. The conclusion is about the supplied work under the observed conditions. It is not a universal benchmark score.

Practical work happens in a separate Linux terminal. The browser runs no commands. Use the prepared PRA-PR06.2 assignment for the commands in this article. Code with a leading $ shows typed input; omit the prompt. Numeric example tables marked “illustrative” are teaching cases, not supplied substitutes for your own captures.

The declared preparation includes process identity, jobs and signals through PR05, basic filesystem inspection through FS01, and PR06.1. You need no C programming, kernel development, hardware-counter expertise, service administration or automation track. Where a shell loop appears, its complete operation is explained or supplied. Writing a benchmark program is not part of this gate.

Readiness check: three distinctions from PR06.1
  1. A workload takes 8 seconds but accumulates about 2 seconds of CPU time. Has it occupied one CPU throughout?
  2. A map covers 2 GiB while its RSS is 20 MiB. Does that alone prove memory pressure?
  3. A command prints correct-looking text. What is still missing before comparing its performance?

Answers: 1. No: in a single-threaded, one-CPU case it ran for roughly a quarter of the wall interval; it may have waited or been runnable but unscheduled. 2. No: virtual extent is not residency or evidence of reclaim. 3. Check complete required work, exact output or another declared correctness oracle, exit status and preservation conditions. Faster wrong work is not an improvement.

1 · Where can the time go?

A program runs instructions in user space, enters the kernel for operations such as reading or writing, and can stop running while waiting for a resource or its turn on a CPU. The scheduler chooses among runnable tasks. When your process is asleep or waiting on the run queue, its elapsed time still grows. A process can also start children; their work belongs in the measurement if the requested job depends on it.

For one single-threaded task restricted to one logical CPU, CPU time / elapsed time is a useful occupancy estimate. Two seconds of CPU in eight seconds of elapsed time is about 0.25 CPU. If an entire job has concurrent workers, their accumulated CPU time can exceed elapsed time. Do not assume that a value above 1 is an error. State whether you measured one thread, a process with descendants, or the whole machine.

“The CPU is busy” and “my job gets enough CPU” differ. A competing task on the same allowed CPU can make a healthy compression job take longer while doing almost the same amount of CPU work. An I/O wait can also make CPU/elapsed small. The ratio identifies a question; it does not select the explanation by itself.

Too much work

Repeated computation, a costly setting or avoidable process setup can increase CPU time per completed job. A better algorithm or allowed setting may reduce that work.

Too little opportunity to run

A competitor can increase elapsed time with little change in the job’s CPU time. Changing the job’s computation may be beside the point.

2 · Count the work in a declared scope

perf stat accumulates selected event counts while a command runs. A count answers “how much of this event was observed in this scope?” It does not tell you which line of the program caused it. The starting command is deliberately narrow:

$ perf stat -e task-clock,context-switches,page-faults -o evidence/baseline-1.stat -- \
    bash -c 'gzip -n -6 -c -- data/example.bin > work/baseline.gz'
  • -- ends perf’s options. The command after it is measured. Descendant counting is normally inherited; do not use --no-inherit for these shell-and-utility jobs.
  • task-clock accumulates scheduled task time; context-switches and page-faults count their selected events. Record the actual event names, modifiers and units printed by your build. Task-clock is not automatically a user-mode-only stopwatch: inspect reported user/system times separately when that distinction matters.
  • -o writes the statistics to a separate text file. The inner shell redirects the workload’s compressed bytes to work/baseline.gz. It does not redirect perf’s own report into that file.
  • gzip -c keeps the input and writes compressed data to standard output. -n omits the stored original name and timestamp. -6 chooses a compression level, not a promised speed.

Use the same declared counting set throughout a comparison. A tool may display a :u modifier because of its access policy. Software-clock accumulation can still include scheduled kernel execution: the printed suffix alone does not turn task-clock into user CPU accounting. By contrast, our later cpu-clock:u samples select user execution locations. Keep those denominators distinct. If the requested observations cannot be collected as declared, report the facility issue. Some builds display task-clock in milliseconds, others expose a raw count without a visible unit; use the supplied release-matched event description to normalize it. Never interpret a billion raw clock units as a billion seconds.

The total page-fault event includes faults resolved without storage I/O. First touches, mappings and copy-on-write can generate faults during ordinary startup. Return to PR06.1 for minor/major distinctions and system reclaim evidence. In this gate faults help contextualize a run; a low fault count is not a universal performance goal.

Predict: what does this repeated command write?
perf stat -r 3 -- gzip -n -6 -c data/example.bin > work/result.gz

The outer shell opens one output file for the whole repeated perf command. Each run appends its output to that same open stream. The file contains three gzip members, and decompression returns three copies of the input. It can pass gzip -t while violating the requested work result. In this pilot use three independent runs with separate reports and output paths, or put the overwrite inside the measured command. The former makes every run easier to inspect.

Unavailable is a different result from zero

<not supported>, <not counted>, a permission error or a failed command is not a measured zero. Hardware events can be unavailable or multiplexed: perf may scale a count from the fraction of the interval in which its event was scheduled. Record that coverage. For this pilot use tested software events and do not grade an IPC or cache-miss threshold. Missing required facilities are assignment faults to report before judging the learner; changing global security settings is outside the task.

3 · Sample where execution happens

perf record collects event-triggered samples into a binary profile. A cpu-clock:u profile samples user-space running activity. It is not a trace of every instruction, every call or every second spent waiting. A sampling frequency of 99 requests roughly 99 samples per second of the relevant running activity; actual collection can vary.

$ perf record -e cpu-clock:u -F 99 -o evidence/baseline.data -- \
    bash -c 'gzip -n -6 -c -- data/example.bin > work/profile-baseline.gz'
$ perf report --stdio --no-children --show-nr-samples \
    --sort comm,dso,symbol -i evidence/baseline.data \
    > evidence/baseline.report

-F 99 requests frequency-based sampling. -i selects the profile to read. --stdio creates an ordinary text report instead of requiring the interactive terminal interface. --no-children avoids call-chain accumulation in the displayed overhead; we have not requested call graphs. Counting and sampling are separate runs, and sampling adds overhead. Compare baseline and correction using equivalent stat runs, not a timed baseline against a profiled candidate.

# Illustrative excerpt, not a required symbol or measured answer
# Samples: 650 of event 'cpu-clock:u'
# Overhead  Samples  Command  Shared Object  Symbol
    65.0%      ...  gzip     gzip           [.] a compression routine
    18.0%      ...  gzip     libc.so.6      [.] a copying routine
     ...       ...  ...      ...            ...

Command is the task name. A DSO (“shared object” in the display) is the executable or library containing the sampled address; the main gzip executable counts too. A symbol is a function name if matching symbol information permits that mapping. An unresolved address may still be attributable to a known executable. It cannot support a claim about a named function. Missing or mismatched binaries and symbols are a visibility problem to disclose, not evidence that the work did not happen.

The overhead column describes a share of the selected sample periods in this report. With a single reasonably stable CPU-clock event and no filtering it can approximate where user CPU time was spent. It is not an exact percentage of elapsed time. Filters change the denominator; call-chain “children” shares can overlap. Keep the selected event, report options, sample count, lost-sample warnings, binaries and observation scope with your interpretation.

Explore the missing wait

Model assumptions: one task, one CPU, exactly 2 seconds of user execution, no kernel time, and 80% of its CPU samples in routine X. Add waiting without changing its computation.

Elapsed: 8 s. Routine X remains 80% of CPU samples; estimated CPU time in X remains 1.6 s. That is 20% of the elapsed interval.

Arithmetic model, not a speedup prediction. Without JavaScript: at 0, 6 and 8 seconds of waiting, elapsed is 2, 8 and 10 seconds; X’s sample share remains 80%, while 1.6 seconds is 80%, 20% and 16% of elapsed. The waiting cause still needs investigation.

Predict: can an 80% hot spot explain an eight-second delay?

Not from that percentage alone. If user CPU time is only 2 seconds, 80% suggests about 1.6 seconds of that CPU work under the model. The other six seconds may be competition, I/O or another wait. Even removing X’s work would not automatically remove the waiting. Look for a second observation and test a permitted change.

Short runs can produce sparse or unstable samples. Enlarge the work using the assignment’s supplied repetition factor; do not raise sampling frequency blindly. Too much sampling can distort the workload or lose records. The assessments state a minimum usable sample count and an attribution rule. They do not require you to reproduce a particular symbol ranking.

4 · Make two observations agree

A useful investigation connects a mechanism with evidence that could have turned out differently. Start with a finite set of possible explanations, identify what would distinguish them, and collect that second observation. You do not need to inspect every event in perf list.

Compression is a tradeoff with a correctness boundary

GNU gzip levels -1 through -9 select speed/compression tradeoffs; the default is -6. A smaller compressed file can cost more work. The fastest permitted setting depends on both the data and the assignment’s size limit. A valid change keeps the exact original bytes recoverable and meets that limit. “All lines seem present” is weaker than byte equality.

$ gzip -t work/baseline.gz
$ gzip -dc work/baseline.gz > work/recovered.txt
$ cmp -- data/example.bin work/recovered.txt
$ wc -c work/baseline.gz

gzip -t checks stream integrity. cmp, when it exits 0, establishes byte equality for these two complete files. A valid gzip stream can still contain the wrong data or repeated copies. Capture exit status and output size; keep the protected input unchanged. Compression level may change compressed bytes while leaving the required decompressed bytes identical.

Competition is about a declared scope

Affinity restricts which logical CPUs a task may use. Two CPU-bound single-threaded tasks pinned to one logical CPU must share it even if other CPUs exist. In the practice and one assessment, the starting sheet identifies that CPU and a disposable optional yes process. This is a controlled way to observe scheduling competition, not a recommendation to pin production work.

top -b -d 1 -n 6 -p WORK_PID,COMPETITOR_PID
taskset -pc WORK_PID
taskset -pc COMPETITOR_PID

Replace the PID placeholders with freshly verified current identities. Ignore the first top frame for an interval comparison; later frames describe updates. A low-priority task can still run when no higher-priority work needs that CPU. Increasing a task’s nice value gives it less favorable scheduling weight; the exact speed effect depends on policy and other runnable work. Use the disclosed permitted control, then observe. Never signal jobs simply because their name resembles the target.

Batching can remove setup without removing input

Launching a utility for every small input repeats executable startup, library loading and process management. A utility may support several operands in one invocation. For GNU gzip, -c with multiple input files writes separate compressed members to one output stream in operand order. Decompressing them concatenates the member contents. That behavior is documented; it does not mean all utilities treat multiple files identically.

Repeated launches

for file in data/pieces/piece*; do
    gzip -n -3 -c -- "$file"
done > work/members.gz

The shell expands the fixed, zero-padded filenames in the declared LC_ALL=C order. It runs gzip once per file. This supplied loop means “perform this command for each path”; no script design is assessed.

One launch, same members

gzip -n -3 -c -- data/pieces/piece* \
    > work/members.gz

GNU gzip receives all operands at once. The task must fit the system’s argument-size limit. This is not permission to omit a file, reorder the logical data or substitute a precomputed result.

A prepared strace observation can corroborate launch count:

strace -f -e trace=execve -o evidence/launches.log -- bash work/pieces-loop.sh

execve replaces a process image with a program. -f follows descendants; the filter records these execution requests rather than all system calls. Inspect successful execve(...)=0 entries for the relevant executable and distinguish the initial shell from gzip. A failed search-path attempt is not another completed gzip job. Run this separately from the timed comparison: tracing perturbs performance. Counting launches from source alone predicts what should happen; observing execution checks what actually happened.

5 · Change a cause, preserve the job

Before changing anything, write a testable proposal using the supplied choices. You may record it in a short table: proposed cause; the two observations supporting it; one allowed change; the result that would weaken your explanation. This is useful investigation practice, not an essay grade. Assessed conceptual items use bounded choices with separate keys.

ObservationJustified next trialRequired protection
Most available CPU goes into compression; a smaller file is not required beyond a published ceiling.Try a documented permitted level and compare time, compressed size and exact recovery.All input bytes and required passes; no cached prebuilt archive.
Job CPU is similar, elapsed grows, and the optional competitor shares its allowed CPU.Use only the allowed control on the identified optional competitor.Required workload, protected peer job and affinity/limits.
Many small inputs cause many observed successful utility launches.Try the documented multiple-operand form and verify member order and complete recovery.Every input, level, repetition count and output contract.

A profile helps choose a plausible trial. The repeated counter/result comparison tests whether that trial helps. You must not call an observed difference causal while also changing input size, CPU placement, compression level and competitor state at once. If the assignment permits several corrections, test one at a time and retain the evidence. An alternative valid approach can pass if it meets the same declared evidence and invariants.

A faster failure fails. Empty output, an early exit, omitted records, fewer passes or a stopped required process can reduce time and counters. Verify correct work on every measured run, not only once after finding a promising number.

6 · Compare repeated, equivalent work

Warm up as specified by the assignment, then collect at least three separate baseline stat runs and three separate correction runs. Use independent output/report names. Keep inputs, repetition count, event set, affinity and any protected workload unchanged. Profile baseline and correction separately with the same sampling event and options. The practice supplies the exact commands.

For a three-run set, the median is the middle elapsed value after sorting. A simple spread measure is (maximum − minimum) / median. It is not a confidence interval. It flags conditions too unstable for this small comparison. A published acceptance band makes the attempt assessable; it is not a claim that three runs settle all performance questions.

Illustrative case: stable improvement versus ambiguous noise
StateThree elapsed timesMedianWhat follows
Baseline8.1, 8.0, 8.2 s8.1 sSpread ≈ 2.5%.
Correction 15.8, 5.9, 5.7 s5.8 sAbout 28.4% less elapsed; verify same work and corroborating counters.
Correction 2 in another trial6.0, 9.0, 7.9 s7.9 sSpread ≈ 38%; the small median change is not dependable evidence.
Work it out: is the first correction a pass?

The timing relationship supports a useful improvement: (8.1 − 5.8) / 8.1 ≈ 0.284. It is not enough for a pass by itself. You still need actual required profiles, coherent scope and second observation, correct output for each run, permitted changes and preservation. Conceptual answers must also pass independently. A shorter elapsed time cannot compensate for one of those failures.

The assessment briefs use a provisional 15% median elapsed improvement and a 15% within-state spread limit; author preflight must show a larger margin on the accepted environment. These numbers are local comparison tolerances for these fixtures. They are not universal hardware performance targets. If noisy neighbors, missing events or unsuitable sample duration make a valid comparison impossible, preserve what you observed and report the facility issue. Do not keep deleting “bad” runs until a preferred answer appears.

Your evidence packet

  • Real software/kernel versions, input identity, declared CPU and process/child scope, event modifiers and timing units.
  • Three baseline and three correction stat reports, with exit status, elapsed/user/system or normalized task-clock observations and a correctness result for each.
  • Baseline and correction perf.data artifacts you generated, text reports and any sample-loss or attribution limitations.
  • A relevant second observation: size/setting, actual process competition, or actual execution count.
  • The allowed change, repeated correct output and protected outcomes; then the separately answered bounded conceptual items.

A text file named perf.data or a copied report does not establish practical collection. The specifications describe the current-attempt execution observations needed; they do not implement a trusted observation system.
