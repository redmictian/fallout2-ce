Make a measurement answer a question.

A smaller time can mean better work, less work, or a different opportunity to run. Build a comparison that tells them apart, then use a real profile without asking it to explain what it did not observe.

1 · Predict what each observation can establish

Before collecting anything, predict which observation could support each claim: (a) the decoded output contains all input bytes; (b) the workflow consumed about two CPU-seconds; (c) most selected user samples were executing gzip; (d) another process consumed much of the same CPU's opportunity. One observation may be needed alongside another.

Compare the scope of your answers

(a) Decode the whole gzip stream and compare bytes to the source; a successful filename or exit status is insufficient. (b) Read process-scoped task-clock for the complete workflow and its children. (c) Inspect your actual cpu-clock:u profile by command and DSO. (d) Inspect real interval CPU use of the relevant identities on the same affinity CPU; a selected-workload profile does not automatically include its unrelated neighbour. None alone proves all four claims.

2 · Establish a complete baseline

Prepare a file work/level6.sh containing the following ordinary Bash command recipe. This recipe runs real GNU gzip sixteen times; it is not an application interface to implement. Use the prepared editor or the literal command block supplied in the terminal assignment.

#!/bin/bash
set -eu
for pass in {1..16}; do
  gzip -n -6 -c -- data/example.bin > "out/pass-$pass.gz"
done

-n omits original filename/time in the gzip header, -6 selects a documented compression level, and -c writes compressed bytes to stdout. Redirection is inside the loop and measured execution. The source is preserved. Run one unmeasured warm-up, then three separate real counting runs.

taskset -c C bash work/level6.sh
taskset -c C perf stat -o evidence/level6-1.stat \
  -e task-clock,context-switches,page-faults -- bash work/level6.sh
# Repeat the same command as level6-2.stat and level6-3.stat.

Read all three logs. Make a table with elapsed time, task-clock and completed passes. Sort the three elapsed values mentally or on paper; the middle value is the median. Compute the run spread as (max − min) / median. A large spread is a reason to inspect conditions and repeat an entire block, not to keep only the fastest run.

# Check every final pass; retain upstream failures as failures.
set -o pipefail
for pass in {1..16}; do
  gzip -t -- "out/pass-$pass.gz"
  gzip -dc -- "out/pass-$pass.gz" | cmp - data/example.bin
  wc -c < "out/pass-$pass.gz"
done

Equal comparisons print nothing and exit 0. These final checks verify the retained outputs. In an assessment, the complete real work during each counting/profile run must also be observed; final files alone cannot prove sixteen executions occurred.

Why not use one outer redirection with perf's repeat option?

perf stat -r 3 -- gzip -c data/example.bin > all.gz repeats gzip but leaves one shared outer output redirection open. It concatenates three streams, so decoding produces the source three times. Keeping redirection inside the measured recipe gives each run the intended output. This practice retains separate stat logs to make each comparison visible.

3 · Obtain your own usable profile

Count first, then sample a separate execution. A 16 MiB input may be too short for stable sampling. For profiling only, copy the recipe to work/profile6.sh and change sixteen passes to 128; disclose that difference. Use the same profile work for the later candidate. The larger repetition supplies more actual events; it is not a way to invent samples.

taskset -c C perf record -F 99 -e cpu-clock:u \
  -o evidence/level6.perf.data -- bash work/profile6.sh
perf report -i evidence/level6.perf.data --stdio --no-children \
  --sort comm,dso,symbol --show-nr-samples > evidence/level6.report

Open the report. Record event, requested/effective frequency, sample count, any lost/throttled warnings, major commands and DSOs. Aim for at least 200 usable user-event samples; if there are fewer, increase the profile-only repetitions for both states equally and collect again. If most DSOs are unidentified, the preparation needs repair. Missing function names can remain an explicit limitation here: do not rename an unresolved address into a guessed function.

Predict: if gzip has 80% of selected sample weight, does it follow that gzip accounts for exactly 80% of elapsed wall time?

Reveal the interpretation

No. This profile samples selected user-mode CPU activity in the workflow and inherited children. Its histogram is normalized to observed selected-event weight. Waiting to run, sleeping, some startup/kernel costs and unrelated processes are not represented by that percentage. A hot DSO is a useful location observation, not a complete wall-time explanation.

Copy work/level6.sh to work/level3.sh and change only -6 to -3. Copy the longer profile recipe similarly. Predict which quantities may change: decoded bytes, compressed bytes, CPU consumed, elapsed time, sample percentage. Lower gzip levels trade compression work and size; do not assume the tradeoff satisfies an unstated business requirement.

5 · Observe scheduling opportunity separately

Now keep the gzip workflow at level 6. Create one explicitly disposable same-owner CPU consumer; yes repeatedly writes its default text to /dev/null and has no required output in this practice. Identify and record its PID before starting the workload.

taskset -c C /usr/bin/yes > /dev/null &
competitor=$!
ps -p "$competitor" -o pid,ppid,user,ni,comm,args
taskset -pc "$competitor"
taskset -c C bash work/profile6.sh &
workflow=$!
ps --ppid "$workflow" -o pid,ppid,comm,args
# Select the live gzip child PID from this observation, not the shell PID.
top -b -d 1 -n 6 -p GZIP_PID,COMPETITOR_PID
wait "$workflow"

Use your observed PIDs. Ignore top's first frame and inspect later interval frames. A selected child can finish before the next frame; repeat the untimed observation or identify its successor if necessary. The parent shell's low CPU does not mean its gzip children did no work. Compare three complete level-6 counting runs with this competitor against three without it; use the same work and warm-up. Stop only the recorded disposable competitor:

kill -TERM "$competitor"
wait "$competitor"             # signal termination is expected here

Predict: if elapsed falls substantially after the optional competitor is gone, while selected task-clock changes little, what was reduced?

Separate work from opportunity

The useful computation can consume similar CPU time but obtain it sooner when it competes less for the allowed logical CPU. The live interval observation and fixed affinity make contention plausible. A gzip user-CPU histogram alone does not directly measure runnable waiting. Stopping a required useful service to get a better number would fail an assessment; this explicitly optional process is different.

6 · Observe launches and preserve gzip member boundaries

Return to the initial no-competitor condition. Consider this real multi-file workflow, saved as work/pieces-loop.sh:

#!/bin/bash
set -eu
export LC_ALL=C
for f in data/pieces/piece*; do
  gzip -n -3 -c -- "$f"
done > out/pieces.gz

Run it once and copy out/pieces.gz to work/pieces-reference.gz. Its 32 independent compressed members decode to the original file. GNU gzip also accepts several file operands with -c, producing separately compressed members in operand order. Save this candidate as work/pieces-batch.sh:

#!/bin/bash
set -eu
export LC_ALL=C
gzip -n -3 -c -- data/pieces/piece* > out/pieces.gz

Predict whether (a) the decoded bytes, (b) compressed bytes under this same binary/level/unnamed headers, and (c) number of gzip launches will match.

bash work/pieces-batch.sh
gzip -dc -- out/pieces.gz | cmp - data/example.bin
cmp out/pieces.gz work/pieces-reference.gz
taskset -c C strace -f -e trace=execve -o evidence/loop-exec.log \
  bash work/pieces-loop.sh
taskset -c C strace -f -e trace=execve -o evidence/batch-exec.log \
  bash work/pieces-batch.sh

Inspect successful gzip execve records: 32 in the loop, one in the batch. Ignore Bash startup and failed executable-path searches. This is direct process-image execution evidence, not an all-system-call profile. A trace perturbs timing, so measure separately without strace if comparing times. For longer perf captures, repeat each complete workflow the same disclosed number of times. A tiny 32-piece example may show little meaningful timing signal; the execution distinction is still observable.

Member behavior and the correct scope of the conclusion

Both comparisons should succeed for the fixed same-version gzip -n -3 work. Each input remains a separate member; batching reduces launches while preserving bytes. Compressing concatenated plaintext into one member can decode to the same data yet violates a requirement to preserve independent members. gzip -l is not the entire decoded-size oracle for a multi-member file. The command documentation and actual exec evidence justify what changed; a user-CPU profile alone does not account for every startup/kernel cost.
